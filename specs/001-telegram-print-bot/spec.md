# Feature Specification: Telegram-бот печати документов

**Feature Branch**: `001-telegram-print-bot`

**Created**: 2026-09-08

**Status**: Draft

**Input**: User description (task.md): "Нужно написать питон бот для тг, который будет хоститься на компьютере windows. Суть его в том что можно будет кидая файлы docx в первую очередь отправлять на печать. Будут подключены только два типа принтеров (всего их не понятно сколько будет) pantum 5100 и gm1033adn. Сценарий такой, заходишь в бот кидаешь файл, будет выбор односторонний или двухсторонний и кол-во копий. Остальное уточни"

**Clarifications (2026-09-08)**: поддерживаемые форматы — DOCX и PDF; доступ — по общему коду доступа с возможностью смены администратором; журнал заданий хранится бессрочно.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Печать документа с базовыми параметрами (Priority: P1)

Сотрудник открывает чат с ботом, отправляет файл DOCX или PDF, бот спрашивает режим печати (односторонняя / двусторонняя) и количество копий, показывает итоговую сводку задания, пользователь подтверждает — документ выходит на принтере, а бот сообщает, что задание отправлено на печать.

**Why this priority**: Это единственный сценарий, ради которого создаётся продукт. Без него бот не имеет ценности; с ним одним продукт уже полностью пригоден к ежедневному использованию.

**Independent Test**: Отправить в бот корректный DOCX, пройти диалог выбора параметров, подтвердить — проверяется по факту наличия распечатанного документа с нужным числом копий и нужным режимом сторон, а также по сообщению-подтверждению в чате.

**Acceptance Scenarios**:

1. **Given** пользователь имеет доступ к боту и принтер готов к печати, **When** пользователь отправляет файл DOCX, выбирает «односторонняя» и 1 копию и подтверждает задание, **Then** документ печатается в одном экземпляре на одной стороне листа, а бот присылает подтверждение с параметрами задания.
2. **Given** пользователь отправил DOCX и выбрал «двусторонняя», **When** он указывает 3 копии и подтверждает, **Then** печатаются 3 экземпляра документа с печатью на обеих сторонах листа.
3. **Given** пользователь отправляет файл PDF, **When** он проходит тот же диалог выбора параметров и подтверждает, **Then** документ печатается с теми же параметрами и в той же последовательности шагов, что и DOCX.
4. **Given** пользователь находится в середине диалога выбора параметров, **When** он отправляет новый файл, **Then** бот начинает новое задание по последнему присланному файлу и явно сообщает, что предыдущий незавершённый выбор отменён.
5. **Given** пользователь выбрал параметры, **When** он нажимает «Отмена» до подтверждения, **Then** задание не печатается, файл удаляется, бот подтверждает отмену.

---

### User Story 2 - Выбор принтера из подключённых (Priority: P2)

Пользователь при оформлении задания видит список доступных принтеров (на старте — Pantum 5100 и GM1033ADN) и выбирает, на каком печатать; недоступные принтеры помечены и недоступны для выбора.

**Why this priority**: В организации несколько принтеров и их число будет расти, поэтому привязка к одному устройству быстро станет ограничением. Но при одном настроенном принтере продукт уже работает, поэтому это второй приоритет.

**Independent Test**: Настроить два принтера, отправить файл, убедиться, что бот предлагает выбор из двух, и что документ выходит именно на выбранном устройстве.

**Acceptance Scenarios**:

1. **Given** настроено два и более принтера, **When** пользователь оформляет задание, **Then** бот показывает список принтеров с понятными названиями и пользователь выбирает один.
2. **Given** настроен ровно один принтер, **When** пользователь оформляет задание, **Then** шаг выбора принтера пропускается и используется единственный доступный.
3. **Given** выбранный принтер не поддерживает двустороннюю печать, **When** пользователь оформляет задание на этом принтере, **Then** вариант «двусторонняя» не предлагается либо помечен как недоступный с пояснением.
4. **Given** администратор добавил третий принтер в конфигурацию, **When** пользователь оформляет следующее задание, **Then** новый принтер появляется в списке без изменения остальных шагов сценария.

---

### User Story 3 - Доступ к боту по общему коду (Priority: P2)

Новый сотрудник запускает бота, тот запрашивает код доступа офиса. После верного ввода пользователь запоминается как разрешённый и больше код не вводит. Посторонний, нашедший бота и не знающий кода, напечатать ничего не может.

**Why this priority**: Бот печатает на физических принтерах в помещении организации, за счёт её бумаги и тонера. Без ограничения доступа любой человек, узнавший имя бота, может печатать что угодно. Ценность защитная, поэтому приоритет ниже основного сценария, но выше удобств.

**Independent Test**: Обратиться к боту из нового аккаунта без кода — убедиться, что печать недоступна; ввести верный код — убедиться, что печать проходит и при следующем обращении код не запрашивается повторно.

**Acceptance Scenarios**:

1. **Given** пользователь ранее не авторизовался, **When** он отправляет боту файл, **Then** файл не печатается, а бот запрашивает код доступа.
2. **Given** пользователь вводит верный код доступа, **When** ввод принят, **Then** пользователь добавляется в список разрешённых и может печатать; при последующих обращениях код не запрашивается.
3. **Given** пользователь вводит неверный код, **When** ввод отклонён, **Then** доступ не предоставляется, а после серии неверных попыток подряд ввод временно блокируется.
4. **Given** администратор сменил код доступа, **When** новый пользователь пытается войти по старому коду, **Then** доступ не предоставляется; ранее авторизованные пользователи продолжают работать.
5. **Given** администратор отозвал доступ у конкретного пользователя, **When** этот пользователь отправляет новое задание, **Then** задание отклоняется и требуется повторный ввод действующего кода.

---

### User Story 4 - Понятная обратная связь по статусу задания (Priority: P3)

После подтверждения пользователь видит, что происходит с его заданием: принято, отправлено на принтер, напечатано или завершилось ошибкой с указанием причины (принтер выключен, нет бумаги, замятие, файл не открылся).

**Why this priority**: Повышает доверие к боту и снижает число повторных отправок «на всякий случай», но базовая печать работает и без детальных статусов.

**Independent Test**: Отправить задание на выключенный принтер и убедиться, что бот сообщает об ошибке с понятной причиной, а не «зависает» молча.

**Acceptance Scenarios**:

1. **Given** задание подтверждено, **When** оно принято в обработку, **Then** пользователь получает сообщение о принятии с номером/идентификатором задания.
2. **Given** принтер недоступен (выключен или отключён от сети), **When** пользователь подтверждает задание, **Then** бот сообщает о недоступности принтера и предлагает выбрать другой или повторить попытку.
3. **Given** задание не удалось напечатать, **When** обработка завершается ошибкой, **Then** пользователь получает сообщение с причиной на понятном языке, а не техническим кодом.
4. **Given** несколько пользователей отправили задания одновременно, **When** задания выполняются, **Then** каждый получает статус только по своему заданию, и задания печатаются без смешивания страниц.

---

### User Story 5 - Обзор заданий и управление доступом для администратора (Priority: P3)

Администратор видит список последних заданий (кто, что, когда, сколько копий, на каком принтере, с каким результатом), может сменить код доступа, отозвать доступ у пользователя, добавлять и удалять принтеры.

**Why this priority**: Нужно для эксплуатации и разбора инцидентов («кто напечатал 200 страниц»), но не требуется для первой работающей версии.

**Independent Test**: Из аккаунта администратора запросить список последних заданий и убедиться, что распечатанные ранее задания в нём присутствуют с корректными параметрами.

**Acceptance Scenarios**:

1. **Given** пользователь является администратором, **When** он запрашивает журнал заданий, **Then** он получает последние задания с автором, именем файла, параметрами, принтером, временем и результатом.
2. **Given** пользователь не является администратором, **When** он пытается запросить журнал, сменить код или изменить список принтеров, **Then** запрос отклоняется.
3. **Given** администратор сменил код доступа, **When** он запрашивает подтверждение, **Then** бот подтверждает смену и новый код действует немедленно, без перезапуска бота.

---

### Edge Cases

- Пользователь отправляет файл неподдерживаемого формата (XLSX, PPTX, JPG, архив) — бот отклоняет файл и явно перечисляет поддерживаемые форматы (DOCX и PDF).
- Пользователь отправляет DOCX как «фото»/сжатое медиа или пересылает файл из другого чата — поведение должно быть одинаковым с обычной отправкой документа.
- Файл повреждён, пуст или защищён паролем (в том числе зашифрованный PDF) — задание отклоняется с понятным сообщением, печать не запускается.
- Файл превышает допустимый размер — бот отклоняет его до загрузки на хост и сообщает предел.
- Пользователь вводит количество копий текстом: 0, отрицательное число, «пять», 10000 — значение отклоняется, бот подсказывает допустимый диапазон.
- Документ содержит очень много страниц — бот предупреждает об объёме и запрашивает дополнительное подтверждение до постановки в печать.
- Пользователь подбирает код доступа перебором — после серии неверных попыток ввод временно блокируется, администратор видит факт попыток в журнале.
- Пользователь бросает диалог на середине и возвращается через час — незавершённое задание истекает по таймауту, файл удаляется, бот сообщает об этом.
- Пользователь отправляет несколько файлов подряд одним сообщением (альбом) — бот обрабатывает файлы по одному, явно указывая, какое задание оформляется.
- Принтер выключен, нет бумаги, нет тонера, замятие — задание не теряется молча; пользователь получает причину и возможность повторить.
- Хост-компьютер перезагрузился или бот был перезапущен с заданиями в очереди — после старта состояние восстанавливается либо незавершённые задания помечаются как неуспешные с уведомлением авторов.
- Пропала связь с интернетом на хосте — после восстановления бот продолжает работу без ручного вмешательства.
- Два пользователя одновременно отправляют задания на один принтер — задания выполняются последовательно, страницы разных документов не перемешиваются.
- В документе используются шрифты, отсутствующие на хосте — вёрстка может измениться; поведение должно быть предсказуемым и, при возможности обнаружения, сопровождаться предупреждением.

## Requirements *(mandatory)*

### Functional Requirements

**Приём и валидация файлов**

- **FR-001**: Система MUST принимать от пользователя файл формата DOCX, отправленный в чат бота как документ.
- **FR-002**: Система MUST принимать и печатать файлы формата PDF по тому же сценарию и с теми же параметрами, что и DOCX.
- **FR-003**: Система MUST отклонять файлы всех прочих форматов (XLSX, PPTX, изображения, архивы и др.) с сообщением, перечисляющим поддерживаемые форматы, и не запускать печать.
- **FR-004**: Система MUST отклонять файлы, превышающие максимально допустимый размер, сообщая пользователю предельный размер.
- **FR-005**: Система MUST отклонять повреждённые, пустые и защищённые паролем документы (включая зашифрованные PDF) с понятным сообщением об ошибке.

**Параметры печати**

- **FR-006**: Система MUST запрашивать у пользователя режим печати: односторонняя или двусторонняя.
- **FR-006a**: Система MUST предлагать выбор формата бумаги A4 или A3 у принтеров, которые печатают на A3, и молча использовать A4 у остальных.
- **FR-007**: Система MUST запрашивать у пользователя количество копий и принимать только целые значения в диапазоне от 1 до 50 включительно.
- **FR-008**: Система MUST предлагать вариант двусторонней печати только для принтеров, поддерживающих её, и пояснять недоступность в остальных случаях.
- **FR-009**: Система MUST показывать пользователю итоговую сводку задания (имя файла, принтер, режим сторон, число копий) и требовать явного подтверждения до отправки на печать.
- **FR-010**: Пользователи MUST иметь возможность отменить оформляемое задание в любой момент до подтверждения.
- **FR-011**: Система MUST завершать незавершённый диалог оформления по таймауту бездействия и удалять связанный файл.

**Принтеры**

- **FR-012**: Система MUST поддерживать одновременное подключение нескольких принтеров и на старте работать с моделями Pantum 5100 и GM1033ADN.
- **FR-013**: Система MUST позволять администратору добавлять и удалять принтеры без изменения пользовательского сценария и без переписывания логики бота.
- **FR-014**: Система MUST предлагать пользователю выбор принтера, когда доступно более одного, и пропускать этот шаг при единственном доступном.
- **FR-015**: Система MUST показывать в списке признак доступности принтера и не позволять отправлять задание на недоступный принтер.

**Выполнение и статусы**

- **FR-016**: Система MUST ставить подтверждённые задания в очередь и выполнять их последовательно для каждого принтера, не смешивая страницы разных заданий.
- **FR-017**: Система MUST уведомлять пользователя о принятии задания и о его финальном результате (успех или ошибка с причиной на русском языке).
- **FR-018**: Система MUST продолжать обслуживать других пользователей, пока выполняется чужое задание.
- **FR-019**: Система MUST корректно вести себя после перезапуска: незавершённые задания либо восстанавливаются, либо помечаются неуспешными с уведомлением авторов.

**Доступ**

- **FR-020**: Система MUST разрешать печать только авторизованным пользователям и отклонять запросы всех остальных.
- **FR-021**: Система MUST запрашивать у неавторизованного пользователя общий код доступа и, при верном вводе, добавлять его в список разрешённых; при последующих обращениях код повторно не запрашивается.
- **FR-022**: Система MUST ограничивать подбор кода: после 5 неверных попыток подряд ввод для этого пользователя блокируется не менее чем на 15 минут, а попытки фиксируются в журнале.
- **FR-023**: Администраторы MUST иметь возможность сменить код доступа; новый код действует немедленно, ранее авторизованные пользователи сохраняют доступ.
- **FR-024**: Администраторы MUST иметь возможность отозвать доступ у конкретного пользователя; после отзыва для печати требуется повторная авторизация по действующему коду.
- **FR-025**: Система MUST различать роли обычного пользователя и администратора и допускать к смене кода, управлению доступом, принтерами и журналом только администраторов.

**Данные**

- **FR-026**: Система MUST вести журнал заданий с автором, именем файла, параметрами, принтером, временем и результатом.
- **FR-027**: Система MUST хранить записи журнала бессрочно; удаление записей возможно только по явному действию администратора.
- **FR-028**: Система MUST удалять загруженный файл документа с хост-компьютера после завершения задания (успешного или неуспешного) и хранить его не дольше срока, необходимого для печати.
- **FR-029**: Система MUST работать без постоянного присутствия администратора за хост-компьютером и автоматически восстанавливать работу после кратковременной потери сети.

### Key Entities

- **Пользователь**: человек, обращающийся к боту. Атрибуты: идентификатор в мессенджере, отображаемое имя, статус доступа (авторизован / не авторизован / доступ отозван), роль (пользователь / администратор), дата авторизации, счётчик и время неудачных попыток ввода кода.
- **Код доступа**: общий секрет офиса, по которому пользователь получает доступ. Атрибуты: текущее значение, дата последней смены, кто сменил.
- **Принтер**: физическое печатающее устройство, доступное с хост-компьютера. Атрибуты: понятное название, модель, поддержка двусторонней печати, признак доступности, признак включён/выключен администратором.
- **Задание печати**: единица работы, созданная пользователем. Атрибуты: автор, исходный документ, имя файла, формат, число страниц, режим сторон, количество копий, целевой принтер, статус (оформляется / принято / печатается / напечатано / ошибка / отменено), время создания и завершения, причина ошибки.
- **Документ**: временный файл, загруженный пользователем. Атрибуты: имя, формат (DOCX или PDF), размер, время загрузки, время удаления. Существует только до завершения задания.
- **Запись журнала**: неизменяемая запись о завершённом задании или значимом событии доступа, хранится бессрочно и служит для эксплуатации и разбора инцидентов.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь, впервые открывший бота, отправляет документ на печать не более чем за 4 шага (не считая однократного ввода кода доступа) и менее чем за 60 секунд, без обращения к инструкции.
- **SC-002**: Не менее 95% заданий объёмом до 10 страниц начинают физически печататься в течение 60 секунд после подтверждения пользователем (при готовом принтере).
- **SC-003**: На контрольном наборе из 20 типовых документов (не менее 5 из них — PDF) не менее 95% печатаются с сохранением исходной вёрстки (разбиение на страницы, поля, таблицы) без ручного вмешательства.
- **SC-004**: 100% выбранных пользователем параметров (число копий и режим сторон) соответствуют фактически напечатанному результату на контрольной выборке заданий.
- **SC-005**: 100% неуспешных заданий сопровождаются сообщением с причиной, понятной без технических знаний; ни одно задание не остаётся без финального статуса.
- **SC-006**: Ни один пользователь без верного кода доступа не может инициировать печать (0 успешных заданий от неавторизованных в тестах и в журнале эксплуатации).
- **SC-007**: 100% загруженных документов удаляются с хост-компьютера в течение 10 минут после завершения задания.
- **SC-008**: Добавление нового принтера занимает у администратора не более 10 минут и не требует изменения сценария для пользователей.
- **SC-009**: Бот остаётся доступен не менее 99% времени, когда хост-компьютер включён, и самостоятельно восстанавливается после кратковременной потери сети без ручного перезапуска.
- **SC-010**: При 5 заданиях, отправленных разными пользователями одновременно, все 5 печатаются полностью и без перемешивания страниц.
- **SC-011**: Администратор находит в журнале любое задание за всю историю эксплуатации (кто, что, когда, сколько копий) не более чем за 1 минуту.

## Assumptions

- Каналом взаимодействия является Telegram-бот; иных интерфейсов (веб, десктоп, мобильное приложение) в первой версии нет.
- Бот работает на одном компьютере под управлением Windows, который включён в рабочее время и имеет доступ в интернет; принтеры доступны с этого компьютера (по сети или напрямую) и уже установлены в системе.
- Реализация выполняется на Python — это заданное ограничение, а не предмет данной спецификации.
- Обе стартовые модели (Pantum 5100 и GM1033ADN) поддерживают автоматическую двустороннюю печать; для будущих моделей поддержка дуплекса задаётся в настройках принтера.
- Код доступа известен сотрудникам офиса и распространяется вне бота (устно, во внутреннем чате); при утечке или увольнении администратор меняет его и при необходимости отзывает доступ у конкретных пользователей.
- Список администраторов задаётся в настройках на хост-компьютере при развёртывании и не меняется через бота.
- Максимальный размер принимаемого файла ограничен возможностями мессенджера (порядка 20 МБ для загрузки ботом) — этого достаточно для типовых офисных документов.
- Печать выполняется с настройками по умолчанию для остальных параметров: книжная ориентация, чёрно-белая печать, масштаб 100%, все страницы документа. Выбор диапазона страниц, цветности, ориентации и лотка в первую версию не входит.
- Формат бумаги — A4 по умолчанию; A3 доступен только на принтерах, которые его поддерживают (определяется по драйверу, переопределяется настройкой `supports_a3`).
- Ожидаемая нагрузка — небольшой офис: до нескольких десятков пользователей и до нескольких сотен заданий в месяц; при таком объёме бессрочное хранение журнала не создаёт проблем с размером хранилища.
- В журнале хранятся только метаданные заданий (автор, имя файла, параметры, результат); содержимое документов не сохраняется.
- Язык интерфейса бота — русский.
- Число принтеров со временем вырастет, поэтому список принтеров задаётся настройками, а не зашивается в код; при этом единый механизм печати применяется ко всем моделям.
- Учёт расхода бумаги/тонера, квоты на печать, оплата и интеграция с корпоративными системами (LDAP/AD, бухгалтерия) в объём не входят.
